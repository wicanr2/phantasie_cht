### 擷取完成點

初次 Carol 快照在 309963492 步，PC 為 `2E4E:FF70`，`Hooks.Busy()` 為真，待完成項為 `int86`。此時新語言疊字仍是 Pending，收據的鍵集合卻已含死亡 key，所以 PASS 不能證明全文可見。

只讀探針量到再執行 23 步後，PC 為 `21AF:343B`，`Hooks.Busy()` 變為假，四語均為完整 Shown。正式路線只將該快照增加量到的 23 步，正常輸入不變。隨後用相同 image 乾淨重跑四模式。這是擷取時機修正，沒有修改忙碌閘門或遊戲規則。初次收據只留診斷，不算正式 UI 完成證據。

## 同狀態與獨立畫面核對

- 正式收據為 none、off、on、on-f2，各 222 點，共 888 個原版狀態點。steps、reads、VRAM、映像範圍、完整 1 MiB 及存檔狀態欄位相同。20,000 與 40,000 步取樣的 Layer 雜湊逐點相同。
- 每模式選定 13 個死亡、切換及返回停點；off、on、on-f2 共 39 個收據 PASS，none 的 13 點是 UI SKIP，只供原版狀態基準。關閉覆繪模式維持英文，不將其 PASS 算成四語畫面。
- `death_visual.go` 不呼叫 Resolver、FormatTarget 或 layoutLine 產生期望值。它用字面譯文、ASCII／全形寬度及原版矩形核對全文、置中補白、原始玩家名、Shown 狀態與顏色。四語及回切 zh-TW、兩種倍率共 20 項全文與像素檢查通過；直接與原版整張畫面比較，差異只在上述批准矩形內，沒有缺字。
- 兩個英文視圖都等於原版 framebuffer。兩次回切 zh-TW 都恢復相同像素；切換、Frame 及負對照未改原版完整記憶體。
- 本機副本只刪除 zh-TW 的一列死亡模板，原列恰好出現一次，其餘列不變。相同原版場景的獨立核對以缺少可見死亡列失敗。負對照放在正向畫面驗收後，隨即停止，不用被刪除 catalog 的記錄生命週期當正常返回證據。

長路線有 102 個無疊字的旅行診斷停點；on 與 on-f2 在這些點標為 FAIL。它們只供原版狀態比對，沒有宣稱整條 UI PASS。完成聲明限上述兩個死亡場景、語言往返及正常回合返回；戰鬥勝利、全滅、其餘事件仍按 005 的未量到項處理。
